## Problem Statement

Cascade, RK's AI agent for GCP data engineering, currently tests its BigQuery integration against real BigQuery. Every dev iteration burns BQ scan costs. No existing local BigQuery emulator is good enough for Cascade's use case: goccy/bigquery-emulator is the only credible option, SQLite-backed, one-person-weekend-maintained, 185 open issues.

LocalGCP, RK's unified single-binary GCP emulator, is missing a BigQuery service. It's the conspicuous gap in LocalGCP's coverage.

Two stacked motivations: unblocks Cascade's dev velocity and cuts Cascade's dev scan costs, AND closes the most visible gap in LocalGCP's service lineup.

## What Makes This Cool

Push what a BigQuery emulator can do to the farthest possible. Greenfield, designed from scratch around DuckDB's strengths. Two v0.1 differentiators no existing BigQuery emulator has:

1. **GCS/Parquet federation** via DuckDB's `httpfs` extension (through a local signing proxy for ADC credentials). Query real production Parquet/CSV from GCS live, at DuckDB speed, through a BigQuery API surface.
2. **Real dry-run cost projection** — compute bytes-scanned from DuckDB's query plan and return it in BigQuery's dry-run response shape. Conditional on the day-4 spike delivering ≤20% fidelity delta on ≥80% of Cascade queries.

Plus one v0.1 **validation tool** (not framed as a differentiator):

3. **Opt-in contract-test mode** — when enabled explicitly, samples queries against real BigQuery, diffs results, logs per-developer fidelity metrics to local JSON + stderr. Default: OFF. It's a tool users reach for, not an identity claim.

Posture: _"the most capable local BigQuery runtime, powered by DuckDB."_ Aspirational ceiling, not comparative position.

## Recommended Approach — Detailed

### Product

BigQuery Emulator, a service inside LocalGCP. Positioning line:

> _"The most capable local BigQuery runtime. DuckDB engine, BigQuery API, Cascade-quality. Part of LocalGCP."_

### Architecture layers

**Layer 1 — API front door.**
Go HTTP server implementing BigQuery REST API (`jobs.insert`, `jobs.query`, `jobs.get`, `jobs.list`, `jobs.getQueryResults`, `jobs.cancel`, `datasets.*`, `tables.*`, `tabledata.list`, `routines.*` as limited set — SQL-only UDFs; scripting and JS UDFs return `UNSUPPORTED_FEATURE`). Storage Read API is **excluded**; clients requesting it get `UNSUPPORTED_FEATURE`. Inbound API auth accepts any bearer token in v0.1; no IAM simulation.

**Data ingestion for tests** happens via two side-channel paths (neither is the Storage Write API):
- DDL: `LOAD DATA INTO <dataset.table> FROM 'file://path/to/data.parquet'` (also accepts CSV, JSON). Executes synchronously, returns a `jobComplete: true` response.
- CLI: `localgcp bq load <dataset.table> <path>` for scripted setup outside the query path.

Both paths are the only way data enters the emulator in v0.1. Real BigQuery load jobs, `tabledata.insertAll` streaming, copy jobs, and extract jobs are excluded.

**Layer 2 — GoogleSQL compatibility layer (the lowering pass module).**
A dedicated `internal/lowering` package sits between the API front door and the DuckDB execution engine. It takes a resolved AST from `goccy/go-zetasql` (the **lower-level** binding that exposes ZetaSQL's analyzer and AST walker), walks it, and emits DuckDB SQL plus a metadata delta.

**Clarification — `go-zetasql` vs `go-zetasqlite`:** These are two separate packages. `goccy/go-zetasql` is the Go binding for Google's C++ ZetaSQL library — it exposes the parser, analyzer, and `ResolvedAST` walker. `goccy/go-zetasqlite` is a higher-level SQLite driver built on top of `go-zetasql` that implements its own lowering pass from ZetaSQL → SQLite SQL. **Our dependency tree:** we depend on `goccy/go-zetasql` directly for parsing and AST analysis. We **read** `goccy/go-zetasqlite`'s lowering code as a reference for rewrite patterns, but we do not depend on it at the module level — our lowering pass targets DuckDB, not SQLite, so we write our own from patterns learned there.

**Day-0 API verification (blocking):** before day-2 spike starts, verify the exact public API entry points on `goccy/go-zetasql` for `(a) ParseStatement(sql)`, `(b) Analyze(parsed, catalog)`, `(c) ResolvedAST tree walker`. Names may differ from these placeholders; the doc cannot commit to exact method names without source inspection.

Where DuckDB syntax supports a BQ construct directly, the lowering pass emits it verbatim. Where it diverges (QUALIFY → equivalent ROW_NUMBER subquery; PIVOT → CASE aggregate rewrite; BQ UNNEST with correlated refs → DuckDB UNNEST with explicit JOIN; ARRAY subscripts → DuckDB list indexing; MERGE → DuckDB UPSERT/MERGE), the lowering pass applies a documented rewrite. Unsupported constructs return `UNSUPPORTED_FEATURE` with the construct name. This module is the heart of correctness; it is also the highest-risk v0.1 work item.

**Layer 3 — Execution layer.**
DuckDB 1.3.x embedded in-process. Native STRUCT/LIST/MAP/JSON. `httpfs` extension for GCS federation via a local signing proxy (see Feature 1). Queries run **serialized** in v0.1 — DuckDB single-writer + multi-reader, but v0.1 does not yet exploit the multi-reader path for concurrent query execution. **Known limitation:** clients issuing multiple concurrent queries (e.g., dbt default 4-thread mode) will see serialized execution. Day-1 audit must check Cascade's concurrency model; if Cascade relies on parallel query submission, this becomes a scope gate.

**Layer 4 — Metadata and control plane.**
Projects, datasets, tables, views, routines, jobs, result handles, and compatibility flags tracked in dedicated internal DuckDB schemas (`_meta.projects`, `_meta.jobs`, `_meta.tables`, etc.). Persistence: single file-backed DuckDB database containing both user data and `_meta.*` schemas. Survives restarts. Result handles are materialized into DuckDB result tables with a 1-hour TTL; `jobs.getQueryResults` paginates via offset+limit over these tables; large results are not streamed.

### Partitioning and clustering in v0.1

- `CREATE TABLE ... PARTITION BY DATE(col)` accepted, persisted in metadata. Data stored in a single DuckDB table; partitioning is **logical only**. `_PARTITIONTIME` / `_PARTITIONDATE` pseudo-columns work via synthetic projection.
- Partition pruning happens during query planning (filters on partition columns influence the bytes-scanned estimate in dry-run mode and skip row groups at execution time via DuckDB's normal predicate pushdown).
- `CLUSTER BY` is accepted, persisted in metadata, **cosmetic in v0.1** (no execution impact). Documented as a known gap.
- Supported `INFORMATION_SCHEMA` views in v0.1: `TABLES`, `COLUMNS`, `PARTITIONS`, `JOBS`, `JOBS_BY_PROJECT`, `ROUTINES`, `VIEWS` (the dbt-essential set plus the two the previous spec missed). All other INFORMATION_SCHEMA views return `UNSUPPORTED_FEATURE`.

### Job lifecycle and async semantics — disambiguated

- `jobs.query` is the **synchronous** query path. v0.1 executes inline and returns `jobComplete: true` in the first response.
- `jobs.insert` is the **generic async** job submission path. v0.1 executes synchronously under the hood but fakes the async state machine in metadata: returns a `Job` resource with state=`RUNNING`, the caller polls `jobs.get`, which returns state=`DONE` on the first poll (since execution already finished during `jobs.insert`).
- `jobs.list` supports pagination.
- Job IDs are deterministic in test mode (seed configurable via env var).
- `jobs.cancel` is a no-op returning success in v0.1 (documented).

### Feature 1 — GCS/Parquet federation

`CREATE EXTERNAL TABLE` DDL maps to BigQuery's external table semantics. The emulator accepts queries against external tables that reference real GCS paths. DuckDB `httpfs` executes them.

**GCS auth plan: signing proxy is the baseline, not a fallback.** DuckDB 1.3.x `httpfs` supports GCS via HMAC keys only; ADC is JWT-based and not natively supported.

**Primary interception mechanism (committed): `s3_endpoint` override with plaintext.** DuckDB's `httpfs` accepts an `s3_endpoint` config override and can be pointed at a local HTTP endpoint instead of `storage.googleapis.com`. Implementation:
1. A local Go signing proxy binds to `127.0.0.1:9070` (or LocalGCP-assigned port, localhost-only, plaintext HTTP — no TLS cert needed).
2. DuckDB is configured at startup: `SET s3_endpoint='127.0.0.1:9070'; SET s3_url_style='path'; SET s3_use_ssl=false;` — this redirects all `httpfs` GCS-style requests to the local proxy.
3. The proxy receives the incoming HTTP request, extracts the bucket+object from the URL path, mints a short-lived signed URL using Cascade's ADC credentials via `google.golang.org/api/storage/v1`, issues a ranged GET against the real `storage.googleapis.com` over HTTPS, and streams the response body back to DuckDB.
4. Signed URLs are cached in-memory with a 10-minute TTL to amortize the signing cost across repeated queries.

**Fallback (if `s3_endpoint` override rejects GCS-style URLs): TLS MITM.** A local self-signed cert + `SET ca_cert_file='/tmp/localgcp-mitm.pem'` to tell `httpfs` to trust the proxy. Documented as day 6-7 contingency if the primary path fails.

**Budget: 3 days for the primary path, +1 day contingency for TLS MITM fallback.** 4 days total (day 5-8 of the spike, previously day 5-7). This extends the spike by one day.

### Feature 2 — Real dry-run cost projection (conditional on day-4 spike)

When `jobs.query` is called with `dryRun: true`, the emulator parses/analyzes the query through `go-zetasqlite` without executing it, then computes bytes-projected-to-be-read:

- **Native tables:** sum the bytes of referenced columns after partition pruning, using DuckDB's statistics from `pragma_table_info` + row counts.
- **External tables (v0.1 scope: not covered by dry-run).** Parquet footer reads over authenticated GCS ranged GETs are a research project in their own right (HTTP range GET + signing proxy + decompression + column index resolution + row group statistics). In v0.1, external table dry-run returns `totalBytesProcessed: 0` with a documented note. Full external-table cost projection is a v0.2 goal.

The result is returned in `JobStatistics.Query.totalBytesProcessed`.

**Fidelity target:** day-4 spike runs the **same 20-query corpus as the day-2-3 lowering spike** (not a separate 5-10 query subset). Compares emulator estimate to real BQ dry-run. **Ship gate:** delta ≤20% on ≥80% of queries → feature ships as v0.1 capability. **Identity claim softened:** headline becomes _"cost projection with measured fidelity — see your own fidelity report in the CLI"_ instead of _"never get surprised by a scan bill."_ The earlier claim was unsupported by the 20% ship gate and is corrected.

### Feature 3 — Contract-test mode (validation tool, not a v0.1 differentiator)

An **opt-in** sampling layer between the API front door and the execution layer. **Default: OFF** in all modes. When a user enables it via `localgcp bq contract-test --enable`, every Nth query is also submitted to real BigQuery using the user's own credentials; results are diffed; fidelity metrics are logged to a local JSON file (`~/.localgcp/bq-fidelity.json`) and stderr.

**Diff engine is a real subproject, not free.** v0.1 normalization rules:
- Result sets are compared as unordered multisets unless the query has an ORDER BY, in which case order matters
- Floats compared with epsilon = 1e-9 relative tolerance
- NULL semantics: SQL NULL = SQL NULL for diff purposes
- STRUCT comparison is field-wise with unordered field comparison
- ARRAY comparison respects order (arrays are ordered by BQ semantics)
- TIMESTAMP normalized to UTC before comparison
- NUMERIC/BIGNUMERIC compared at 38-digit precision (truncation warning logged if the BQ result had more precision)

Budget: 5 days of the 90-day build for the diff engine alone. No Prometheus endpoint (stderr + JSON only in v0.1).

**Contract-test cost budget:** when enabled at 10% sampling against real BQ, burns scan costs proportional to sample rate. Users are explicitly warned in docs: _"enable for fidelity validation runs, disable afterwards."_ The emulator keeps its cost-elimination identity cleanly because contract-test defaults to OFF.

## Key Technical Risks (ranked)

**Risk 0 (blocking, day-0 pre-spike check): `goccy/go-zetasql` prebuilt availability.**
Before writing any spike code, verify that `goccy/go-zetasql` publishes current pre-built ZetaSQL binaries for **macOS-arm64 and linux-amd64** at a glibc version compatible with LocalGCP's base image. If prebuilts are missing, stale, or ABI-incompatible, the entire CGO distribution plan falls over and we either (a) build ZetaSQL from source ourselves (multi-day task per platform), or (b) drop to SQLGlot. **This pre-check is 1-2 hours of work and must happen on day 0, before day 1.**

**Risk 1 (highest unresolved): ZetaSQL → DuckDB lowering pass complexity.**
GoogleSQL and DuckDB SQL agree on ~80% of real queries and diverge on the long tail. Mitigation: day-2-3 spike runs the lowering pass against 20 representative Cascade queries. **Kill gate:** if fewer than 16 of 20 queries round-trip correctly, ZetaSQL lowering is not viable for Approach A and we re-scope to Approach C immediately.

**Risk 2: Cost projection fidelity has no prior art.**
DuckDB's query plan doesn't compute "bytes scanned" in BigQuery's sense. The mapping requires computing referenced-column byte sizes from DuckDB statistics and correlating with partition pruning. Mitigation: day-4 spike is a research spike with the 20% ship gate.

**Risk 3: `httpfs` GCS signing proxy.**
Budgeted as baseline (3 days). Risk is auth-permutation edge cases (ADC on developer laptop is simpler than workload identity federation, which is simpler than impersonation chains). v0.1 covers ADC on developer laptop; other auth modes documented as known gaps.

**Risk 4: Contract-test diff engine complexity.**
5 days of build time allocated, but normalization rules for floating-point tolerance, STRUCT field ordering, NUMERIC precision, and TIMESTAMP timezone could expand. Mitigation: v0.1 ships with the rules above; edge cases become follow-up work.

**Risk 5: Single-person capacity split across 4 projects.**
60% allocation is the assumption. Day-30 gate triggers if burn-down math shows <50% effective allocation.

**Risk 6 (compound): any two of Risks 1-3 firing.**
Individual risks at ~20% probability each have a ~48% joint probability that at least one fires. The composite spike outcome matrix (below) defines what happens when 2+ fire simultaneously.

## Reviewer Concerns (open, deferred from iteration 3)

These issues were flagged in the final spec review iteration but are either (a) minor refinements that don't block day-1 start, (b) call-outs best resolved during the spike once real signal is available, or (c) trade-offs the designer chose to defer. They are documented here so downstream skills and the implementer see them:

1. **Result handle TTL + restart behavior:** result tables have a 1-hour TTL, but the behavior on process restart is undefined (cleaned up? left to rot?). **Deferred decision:** result tables cleaned up at startup. `jobs.getQueryResults` on an expired/cleaned result returns `notFound`. Resolve in day 8-12 of the build when the metadata layer is implemented.
2. **`_PARTITIONTIME` semantic trap:** BQ's `_PARTITIONTIME` only exists on ingestion-time partitioned tables, not `PARTITION BY DATE(col)`. If Cascade queries reference `_PARTITIONTIME` on date-partitioned tables, v0.1 should strict-error with a clear message. Resolve in day-1 audit grep.
3. **Day-1 audit artifact schema:** the spreadsheet schema isn't written down. **Minimum columns:** `method`, `http_verb`, `example_payload`, `frequency`, `criticality`, `sql_pattern_id`, `notes`. Engineer picks format on day 1.
4. **Budget math drift for launch post:** Launch checklist says the build-log post is "~2 focused days budgeted inside the 90-day plan" but the day budget table sums to exactly 54 with no blog row. Real total is 56 focused days over 90 calendar days — 2% over budget, absorbed as noise.
5. **Day-30 gate marker asymmetry:** day-30 marker #2 accepts 14/20 queries passing, but spike kill gate is 16/20. The two are fresh-run vs after-22-days-of-work, so 14/20 at day-30 is an acceptable mid-sprint checkpoint, not a regression. Clarified here.
6. **Concurrency gate ambiguity:** if day-1 audit reveals Cascade uses parallel query submission, decision is: **v0.1 ships with a serialization shim on Cascade's side** (easier than building concurrent execution in the emulator); Cascade configures its BQ client for max-parallelism-1 in dev/CI mode. Concurrency as a real emulator feature lands in v1.0.
7. **`LOAD DATA` syntax is emulator-convenience, not BQ-shape:** the form `LOAD DATA INTO <table> FROM 'file://path'` is emulator convenience syntax, not BigQuery's actual `LOAD DATA [OVERWRITE] INTO ... FROM FILES(uris=[...], format=...)`. v0.1 accepts **both** — the BQ-shape form delegates to the same implementation; only file:// URIs are supported in v0.1 (GCS URIs defer to v0.2 alongside Storage Write API).
8. **`jobs.cancel` vs `jobs.insert` synchronous divergence:** a cancel-after-complete call returns `DONE` instead of the real-BQ `DONE` + `errorResult.reason = stopped`. Documented as a known divergence in v0.1; not user-visible for the Cascade test path.
9. **INFORMATION_SCHEMA scope (`PARTITIONS`, `ROUTINES`):** budgeted inside the 4-day partitioning + pruning + cost estimation line item. If these prove too heavy during implementation, `PARTITIONS` drops to a stub returning empty rows and `ROUTINES` is deferred to v0.2. Decided at day 15-20 of the build.
10. **Lowering pass 12-day budget assumes ≤5 hard-rewrite patterns:** if day-1 audit reveals >5 patterns requiring bespoke AST rewrites (QUALIFY, PIVOT, correlated UNNEST, MERGE, others), bump the line item to 15-16 days by borrowing from the 3-day `localgcp bq load` CLI budget (which is over-allocated).
