## Problem Statement

BigQuery is the most conspicuous gap in LocalGCP's 13-service emulator lineup (BigQuery would be service #14). RK's other project, Cascade (AI agent for GCP data engineering), tests against real BigQuery and burns scan costs on every dev iteration. The only existing emulator, goccy/bigquery-emulator, is SQLite-backed, one-person-maintained, and has 185+ open issues.

Two stacked motivations: (1) unblock Cascade's dev velocity and cut dev scan costs, (2) close the biggest gap in LocalGCP's service coverage.

## What Makes This Cool

A new kind of BigQuery emulator, built from scratch around DuckDB's strengths instead of working around SQLite's limitations. Three things no existing BQ emulator does:

1. **GCS/Parquet federation** via DuckDB's `httpfs` extension through a local signing proxy. Query real production Parquet/CSV from GCS live, at DuckDB speed, through a BigQuery API surface.
2. **Real dry-run cost projection** computed from DuckDB's query plan statistics. Conditional on the spike delivering <=20% fidelity delta on >=80% of test queries.
3. **Opt-in contract-test mode** that diffs emulator results against real BigQuery for fidelity validation.

And one structural contribution to the Go ecosystem:

4. **Fresh Go bindings for google/googlesql** (formerly ZetaSQL, renamed February 2026). Nobody has built Go bindings for the renamed library yet. This artifact has value beyond LocalBQ.

Posture: _"the most capable local BigQuery runtime, powered by DuckDB."_

## Key Design Decision: Separate Product

**LocalBQ ships as its own product, not embedded in localgcp.**

Rationale: GoogleSQL (the SQL parser) requires CGO. Embedding it would add ~30-50MB to the localgcp binary and break the "pure Go, zero CGO, 20ms startup" guarantee for every user, including those who never touch BigQuery. That's the wrong trade-off.

Instead:
- **LocalBQ** lives in its own repo (`slokam-ai/localbq`), with its own CLI (`localbq up`), own Homebrew formula, own Docker image.
- **LocalGCP** orchestrates it via the existing Docker lazy-proxy pattern, same as Spanner and Bigtable. One config entry in `orchestrator/config.go`.
- Users who don't need BigQuery never pay the cost. Users who do get it via `localgcp up --services=bigquery` or standalone `localbq up`.

This protects localgcp's core identity while giving LocalBQ room to be its own product.

## Premises (agreed during this session)

1. **Native-style service with lazy init.** LocalBQ starts its REST endpoint immediately. DuckDB + GoogleSQL init deferred to first query. When orchestrated by localgcp, the Docker container starts on first request via lazy proxy.
2. **Own Go bindings for google/googlesql.** No middleman. Build CGO bindings directly against the renamed library. Use goccy/go-zetasql as reference only.
3. **Separate repo, separate product.** `slokam-ai/localbq` with own CLI, Homebrew formula, Docker image. LocalGCP integration is a one-line config entry.
4. **7-day spike first.** Day-0 investigates google/googlesql C++ API surface and minimal CGO binding. Day 2-3 validates lowering pass. Fallback: wrap goccy/bigquery-emulator as Docker image if spike fails.
5. **v0.1 scope holds from prior design.** 2 differentiators + 1 validation tool. No scope cut, no scope creep.

## Approaches Considered

### Approach A: Full Stack (CHOSEN)
Own repo, own Go bindings for google/googlesql, DuckDB execution, all 3 v0.1 features. The "learn everything" path.
- **Effort:** L (~64 focused days at 60% allocation over ~107 calendar days. CGO binding work adds ~10 days to prior design's 54-day budget)
- **Risk:** Medium-High (CGO binding work is estimated, not validated)
- **Pros:** Full control, no middleman. Go bindings become an open source contribution. Learning compounds into Cascade.
- **Cons:** CGO binding work is the new biggest risk. C++ build system (Bazel) adds CI complexity.
- **Completeness:** 9/10

### Approach B: Pragmatic
Start with goccy/go-zetasql, fork if stale. Save own-bindings work for v1.0.
- **Effort:** M (~60 focused days)
- **Risk:** Medium (middleman dependency)
- **Completeness:** 7/10

### Approach C: Minimal + Hero
SQLGlot (Python) parser, skip GoogleSQL for v0.1. Ship fast, add correctness later.
- **Effort:** S-M (~35 focused days)
- **Risk:** Low but contradicts the correctness premise
- **Completeness:** 5/10

## Recommended Approach — Detailed

### Architecture Layers (from prior design, unchanged)

**Layer 1 — API front door.**
Go HTTP server implementing BigQuery REST API subset: `jobs.insert`, `jobs.query`, `jobs.get`, `jobs.list`, `jobs.getQueryResults`, `jobs.cancel`, `datasets.*`, `tables.*`, `tabledata.list`, `routines.*` (SQL-only UDFs). Storage Read/Write APIs excluded from v0.1.

Unsupported features return HTTP 400 with BigQuery-shaped error responses: `{"error": {"code": 400, "message": "...", "errors": [{"reason": "UNSUPPORTED_FEATURE", "message": "...", "location": "..."}]}}`.

Data ingestion via two side-channels (v0.1 supports Parquet and CSV; JSON and Avro deferred to v0.2):
- DDL: `LOAD DATA INTO <dataset.table> FROM 'file://path/to/data.parquet'`
- CLI: `localbq load <dataset.table> <path>`

**Layer 2 — GoogleSQL compatibility layer (the lowering pass).**
A dedicated `internal/lowering` package. Takes a resolved AST from our Go bindings for `google/googlesql`, walks it, and emits DuckDB SQL plus metadata deltas. Where DuckDB supports a BQ construct directly, emit verbatim. Where it diverges (QUALIFY, PIVOT, correlated UNNEST, MERGE, ARRAY subscripts), apply documented rewrites.

**Day-0 API investigation (blocking):** Before spike day 2, verify the `google/googlesql` C++ API entry points for parsing, analysis, and AST walking. Stand up a minimal CGO binding that can parse one SELECT statement. This is the new kill gate.

**Layer 3 — Execution layer.**
DuckDB 1.3.x embedded in-process. Native STRUCT/LIST/MAP/JSON. `httpfs` for GCS federation. Serialized execution in v0.1: all queries (read and write) are serialized behind a single mutex. Concurrent query submission from clients is accepted but executed sequentially. This is simple and correct for dev/CI use; concurrent execution is a v1.0 feature.

**Layer 4 — Metadata and control plane.**
Projects, datasets, tables, views, routines, jobs, result handles in DuckDB `_meta.*` schemas. File-backed persistence. Result handles with 1-hour TTL.

### Partitioning and clustering
- `PARTITION BY DATE(col)` accepted, logical only (no physical partitioning). `_PARTITIONTIME`/`_PARTITIONDATE` pseudo-columns via synthetic projection.
- `_PARTITIONTIME` is only synthesized for ingestion-time partitioned tables, not `PARTITION BY DATE(col)` tables. If Cascade queries reference `_PARTITIONTIME` on date-partitioned tables, the emulator returns a clear error. Resolved during day-1 audit.
- `CLUSTER BY` accepted, cosmetic in v0.1. Documented as known gap.
- INFORMATION_SCHEMA views in v0.1: TABLES, COLUMNS, PARTITIONS, JOBS, JOBS_BY_PROJECT, ROUTINES, VIEWS.

### Feature 1 — GCS/Parquet Federation
`CREATE EXTERNAL TABLE` maps to BigQuery external table semantics. DuckDB `httpfs` executes via a local Go signing proxy:

1. A Go HTTP handler binds to `127.0.0.1:9070` (plaintext HTTP, internal-only, not user-configurable in v0.1).
2. DuckDB is configured at startup: `SET s3_endpoint='127.0.0.1:9070'; SET s3_url_style='path'; SET s3_use_ssl=false;` — this redirects all `httpfs` GCS-style requests to the local proxy.
3. The proxy receives the request, extracts bucket+object from the URL path, mints a short-lived signed URL via ADC credentials (`google.golang.org/api/storage/v1`), issues a ranged GET against real `storage.googleapis.com` over HTTPS, and streams the response back to DuckDB.
4. Signed URLs are cached in-memory with a 10-minute TTL.

Budget: 4 days. Fallback (if `s3_endpoint` rejects GCS-style URLs): TLS MITM with self-signed cert. 1 day contingency.

### Feature 2 — Dry-Run Cost Projection (conditional)
`jobs.query` with `dryRun: true` computes bytes-projected from DuckDB statistics. Native tables only in v0.1. Ship gate: delta <=20% on >=80% of test corpus.

### Feature 3 — Contract-Test Mode (validation tool)
Opt-in, default OFF. Samples queries against real BigQuery, diffs results, logs fidelity metrics. Budget: 5 days for the diff engine.

### New: Go Bindings for google/googlesql
Fresh CGO bindings against `github.com/google/googlesql`. Minimal surface for v0.1:
- `Parse(sql string) (*ParseResult, error)` — parse a SQL statement
- `Analyze(parsed *ParseResult, catalog *Catalog) (*ResolvedAST, error)` — resolve types and references
- `Walk(ast *ResolvedAST, visitor Visitor) error` — traverse the resolved AST

Use `goccy/go-zetasql` as reference for: CGO bridge patterns, memory management, error handling, catalog registration. But our bindings target `google/googlesql` directly.

**Estimated effort:** 10 focused days (C++ Bazel build + CGO bridge + minimal Go API + tests). This is the new biggest risk item. The 10-day binding work starts after the spike concludes and Parse is validated (approximately calendar day 10-20). **Intermediate check at day 5 of binding work (~calendar day 15):** Analyze works on >=5 SQL statements, or escalate to Approach B. The spike kill gate covers Parse only; Analyze and Walk may surface additional Bazel targets or linking requirements.

## LocalGCP Integration

The localgcp side is minimal. Add to `internal/orchestrator/config.go`:

```go
BigQueryConfig = ContainerConfig{
    Name:         "localgcp-bigquery",
    Image:        "ghcr.io/slokam-ai/localbq:latest",
    InternalPort: "9060/tcp",
    DataPath:     "/data", // DuckDB database file persistence
}
```

And add `"bigquery": BigQueryConfig` to `ServiceRegistry`. Update the CLI (add "bigquery" to the `--services` flag help text), the `env` command (export `BIGQUERY_EMULATOR_HOST`), docs, and website. ~half a day of work (not 2 hours, since the env command and docs touch multiple files).

## Explicit v0.1 Exclusions

All return BigQuery-shaped `UNSUPPORTED_FEATURE` errors:
- BigQuery Storage Read/Write API
- Inbound API authentication (accepts any bearer token)
- BigQuery ML / Model API / Connection API / BI Engine
- Real GEOGRAPHY with WGS84 geodesic semantics
- BIGNUMERIC beyond 38 digits
- Row/column-level security, authorized views
- Time travel / FOR SYSTEM_TIME AS OF
- Sessions / scripting / stored procedures / JS UDFs
- Materialized view refresh semantics
- IAM / Reservations / capacity API
- INFORMATION_SCHEMA views beyond the v0.1 set
- CLUSTER BY execution impact
- Concurrent query execution
- External table dry-run cost projection
- dbt-bigquery-local adapter shim
